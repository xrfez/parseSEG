# SEG P1/P2/P3/P4 (1983) positional exchange formats: spec note

Source: `SEG Spec/text/SEG standard exchange formats for positional data- P1 - P2 - P3.txt`
(Morgan, Spradley, Worthington, McClelland, 1983, *Special report on SEG standard exchange
formats for positional data*, Geophysics 48(4), 488-503). `[p.N]` = `=== PAGE N ===` marker.

> **Naming.** The document defines **four** formats, not three [p.1, p.3-4]:
> **P1** postplot location data, **P2** marine positioning *field* data, **P3** *land survey*
> field data, **P4** Transit (Doppler) satellite field data. There is no "marine processed"
> format. This is the 1983 edition ("P1/83"). The later UKOOA P1/90 and IOGP P1/11 formats are
> **different** formats with coded header records; they are not in this source (see §6.3).

Convention deviation: these are 80-column card images, not binary. The tables use **Cols**
(1-based, inclusive, within the 80-column record) and a **Fmt** column (the spec's FORTRAN
edit descriptor) instead of Bytes/Nibble/Enc. Every field is character data: EBCDIC on the
standard tape, ASCII allowed [p.6].

**Example verification.** pdftotext collapsed runs of blanks and stripped some leading blanks in
the figures, so the example lines are *not* column-exact in the text file. I rebuilt each example
from its right-anchored fields and checked every column against the tables:
- **P1:** all 20 records of Fig. A-1 rebuild to exactly 80 columns, and every field lands in its
  table columns (§3.4).
- **P2:** record 1 matches at cols 26-57. Record 2 matches at all 66 columns. Record 3 matches at
  4 × 8 columns. Record 4 matches at 16 × 4 columns, once a stripped leading blank is put back.
- **P3:** cols 29-64 match on all 20 records (right-anchored). Cols 2-17 cannot be checked
  because the leading blanks were stripped.
- **P4:** orbit records 002-005 match exactly (7 × [M.V. char + 9 digits], the M.V. char is `3`
  in every slot), and so do the Doppler record decimal-point columns.

## 2. File / tape structure (common to P1-P4)

| Rule | Value | Ref |
|---|---|---|
| Logical record | 80 bytes (one card image) | [p.6, p.9, p.14, p.18] |
| Block (physical record) | 20 logical records = 1600 bytes, separated by inter-record gaps | [p.6, p.9, p.14] |
| Tape | ½-inch, 9 track, 1600 bpi (800/6250 allowed), EBCDIC (ASCII allowed), odd parity | [p.6] |
| Logical file | header block(s), then any number of data blocks, then **one EOF** | [p.6] |
| End of tape data | the last logical file is followed by a **second EOF** | [p.6] |
| Nothing before the first header | no OS labels, no data before the first header block | [p.6] |
| Header block | **20** × 80-byte records; an `H` in **col 1 of the first record of the block** identifies it. The other 19 records are free text (col 1 is normally blank) | [p.6, p.9, p.14, p.18] |
| Header content | free format; mandatory topics listed per format (§3.1, §4.1, §5.1, §7.1) | |
| Data record identifier | **blank in col 1** (P1, P2 first record of each group, P3). P4 uses `S` (see §7) | [p.7, p.10, p.16] |
| New logical file | P1: a change of grid projection or origin (e.g. a new UTM zone) needs a new logical file with its own header. P2/P3/P4: a change of prime position control or of header specs | [p.6, p.9-10, p.14, p.18] |

> **AMBIGUITY:** [p.18] P4 says "data and header blocking size 100 bytes". That is a typo for
> 1600 (20 × 80). [p.14, p.18] P3/P4 say a second EOF signals "the end of the header". That
> is a typo for "end of the data" (as P1/P2 say).

> **AMBIGUITY:** [p.17] The second header block of Fig. C-1 shows only 13 lines before the data,
> so either the extraction dropped blank lines or the block was short. A reader must accept
> blank/short header blocks. A writer should pad header blocks to 20 records with
> all-blank records.

**Disk files.** Tape marks and block gaps disappear on disk. Accept three layouts: (a)
newline-terminated lines (trailing blanks may be trimmed: pad every line to 80 before
slicing), (b) fixed 80-byte records with no newlines (`size mod 80 == 0`, no `\n`), (c) the same
in EBCDIC (byte 0 = `0xC8` 'H', many `0x40` blanks). Treat an `H` in col 1 *after* data
records as the start of a new logical file (its own header, units and projection).

**Number conventions (FORTRAN formatted I/O)** [p.8, p.12, p.16]:
- `Iw`: right-justified integer, `w` columns.
- `Fw.d`: `w` columns. With **no** decimal point in the field, the decimal point is
  **implicit** before the last `d` digits (`F4.2` "3354" = 33.54). A decimal point written in
  the field overrides `d`.
- `F8.X` / `F5.X`: the decimal count `X` is given in the header (up to 8 decimals) [p.8, p.12].
- `nAk` (e.g. `4A4`): character, n × k columns.
- The spec does not define blanks. Proposed rule: an all-blank field = missing. Treat
  embedded blanks as zeros (FORTRAN 66 `BZ` behavior). The examples zero-pad DMS sub-fields
  ("001275684E"), so readers must accept leading blanks and leading zeros alike.

## 3. P1: postplot location data, SEG P1 (1983)

### 3.1 Header (mandatory free-text topics) [p.6-7]
| Topic | Content |
|---|---|
| a. Area | survey name/area, license block number(s) |
| b. Client | client/operator, geophysical contractor, nav acquisition contractor, nav processing contractor, survey dates |
| c. Positioning | all positioning systems; the point mapped (e.g. centre of source array) and its offset from the antenna/sensor or nav reference point |
| d. Geodetic | ellipsoid name (if in WGS 72), else semi-major axis and flattening; datum name and transformation parameters (e.g. WGS 72→NAD 27 dx=+22 m, dy=−157 m, dz=−176 m); source of the geodetic data |
| e. Projection | name; UTM zone or central meridian; else: projection name, grid origin (longitude of origin + false easting, latitude of origin + false northing), standard parallels (Lambert), origin of longitude if not Greenwich, scale factor and where it is defined |
| f. Units | units of grid coordinates, water depth/elevation, quadrant-reading instrument, etc. |
| g. Survey | conditions; **definitions/identifiers that distinguish seismic from non-seismic events**; what the "shotpoint" field holds when it is not a shotpoint |
| (recommended) | system details, shore base station locations, which stations were used |

No header keywords or codes are standardized. Fig. A-1 uses `KEY: value` lines (`SPHEROID:`,
`PROJECTION:`, `UNITS:`, `FALSE EASTING:`, ...) as an informal convention [p.8].

### 3.2 Data record (one per seismic or non-seismic event) [p.7]

| Cols | Len | Fmt | Field (`nimIdent`) | Meaning |
|---|---|---|---|---|
| 1 | 1 | blank | `recordId` | data record identifier = blank |
| 2-17 | 16 | 4A4 | `lineName` | line name, **left-justified**, alphanumeric |
| 18-25 | 8 | I8 "(or as specified)" | `pointNumber` | shotpoint number, or the event parameter defined in header c/g; right-justified |
| 26 | 1 | A1 | `reshootCode` | blank = original; `A` = first reshoot of a repeated number on the same line, `B` = second, ... |
| 27-35 | 9 | I2,I2,F4.2,A1 | `latitude` | DMS: cols 27-28 deg, 29-30 min, 31-34 sec (implicit 2 decimals), 35 `N`/`S` |
| 27-35 | 9 | (F8.5,A1) | `latitude` (alt.) | grads to 5 decimals: cols 27-34, 35 `N`/`S` |
| 36-45 | 10 | I3,I2,F4.2,A1 | `longitude` | DMS: cols 36-38 deg, 39-40 min, 41-44 sec (implicit 2 decimals), 45 `E`/`W` |
| 36-45 | 10 | (F9.5,A1) | `longitude` (alt.) | grads to 5 decimals: cols 36-44, 45 `E`/`W` |
| 46-53 | 8 | F8.X | `easting` | map grid easting; units and decimals per header |
| 54-61 | 8 | F8.X | `northing` | map grid northing; units and decimals per header |
| 62-66 | 5 | F5.X | `depthOrElevation` | water depth **or** elevation above MSL; header says which, the units and the decimals |
| 67-68 | 2 | I2 | `year` | two-digit year |
| 69-71 | 3 | I3 | `dayOfYear` | 1-366 |
| 72-73 | 2 | I2 | `hour` | GMT |
| 74-75 | 2 | I2 | `minute` | GMT |
| 76-77 | 2 | I2 | `second` | GMT, whole seconds |
| 78-80 | 3 | | `spare` | blank |

Rules [p.7-8]: the position is that of the shotpoint as shown on the seismic section and the
shotpoint map. Non-seismic events may be at constant time intervals or at event times. "By
lengthening the data record, other geophysical information such as gravity and/or magnetic
data could be accommodated" [p.3]. So expect records longer than 80 columns in variants,
and ignore extra columns.

> **AMBIGUITY:** [p.7] The latitude DMS sub-fields sum to 2+2+4+1 = 9 columns (27-35) and the
> grads form to 8+1 = 9 columns. Both fit. The spec does not say which form a file uses: it is
> in the header's unit information. Heuristic: an angle is valid DMS if cols 29-30 ≤ 59 and
> cols 31-34 ≤ 5999 (and the same for longitude). That test cannot be applied per angle: in a
> grads file about four angles in ten pass it. The reader decides once per file, from the
> angles of its first P1 records: grads when more than a tenth of them are not valid DMS, else
> DMS. Default to DMS.

> **AMBIGUITY:** [p.7] There is no column for the seismic/non-seismic distinction. Header g
> defines it in free text, so a reader cannot tell them apart without help.

### 3.3 Coordinate encodings
| Encoding | Decode | Encode (writer) |
|---|---|---|
| Lat DMS `DDMMSSssH` | `deg = DD + MM/60 + SS.ss/3600`, negative if `S` | round to 0.01″ first, then carry 60.00″ → +1′ and 60′ → +1°; zero-pad: `%02d%02d%04d` + hemisphere |
| Lon DMS `DDDMMSSssH` | as above, negative if `W` | `%03d%02d%04d` + hemisphere |
| Lat grads `GGGGGGGGH` (F8.5) | `grads = digits / 1e5` (if no '.'); `deg = grads × 0.9` | `%08d` of `round(grads × 1e5)` + hemisphere |
| Lon grads (F9.5) | same, 9 digits | `%09d` |
| Easting/Northing F8.X | implicit X decimals unless a '.' is present | right-justify in 8; prefer writing an explicit '.' only if the header X matches; otherwise digits only |
| Depth/elevation F5.X | same | same |

Hemisphere letters only: there are no signs in lat/long. The grid units (metres, feet, US
survey feet), datum, ellipsoid and projection are known only from the header text.

| Cols | Text | Value |
|---|---|---|
| 1 | ` ` | data record |
| 2-17 | `CLT4960         ` | line `CLT4960` |
| 18-25 | `   12340` | SP 12340 |
| 26 | `B` | second reshoot |
| 27-35 | `17543354N` | 17°54′33.54″ N = 17.909317° |
| 36-45 | `110445881E` | 110°44′58.81″ E = 110.749669° |
| 46-53 | `  155590` | E 155590 (header: `UNITS: METERS`, Lambert, false E 500000) |

Checked: the shotpoint increases by 10 per record, the time by about 2 min, and the easting
decreases monotonically. The easting is consistent with the header (110.75°E is about 345 km

> which suggests F5.1, but this is not stated. Treat X as header/user supplied (default 0).

> **AMBIGUITY:** [p.8] OCR noise in Fig. A-1: `?` for `7` ("19?" = 197), `SOUIH` (SOUTH),
> `O18000000N` (018...). The header origin values (`021000000N`, 10 chars) are free text,
> not the data-record lat/long format. The record day 197 (16 July 1979) contradicts the
> stated survey dates (Sept 1979 - March 1980). This is an example inconsistency only.

### 3.5 Sort order and validation
- The spec mandates **no sort order**. The example is in acquisition order (line, increasing SP,
  increasing time). The writer should preserve input order.
- Validation: col 1 blank; col 35 ∈ {N,S}; col 45 ∈ {E,W}; cols 27-34 and 36-44 digits (or
  blank); DMS minutes < 60 and seconds < 60.00; lat ≤ 90°, lon ≤ 180°; col 26 ∈ {blank, A-Z};
  day 1-366, hour < 24, min < 60, sec < 60 (blank = unknown).
- One logical file = one grid projection/origin. Don't merge eastings across logical files
  without checking that their header projection text is the same.

## 4. P2: marine positioning field data, SEG P2 (1983)

### 4.1 Header (mandatory free-text topics) [p.9-10]
a. area; b. client (same as P1); c. positioning: all systems and **which is prime**, reference
points, layback antenna→source, offset source→near trace group, group interval, source depth,
geoidal height of the satellite antenna, antenna heights above the waterline, echo sounder
type/model, sound velocity used, transducer depth; d. geodetic (as P1); e. projection (as
P1); f. radio/acoustic systems: reference station geodetic and grid coordinates,
elevations/depths, frequencies, propagation velocities, lane widths, **the assignment of raw
pattern fields to base stations** (a change needs a new header), source of the base station
data; g. **meaning of reference parameters 1 and 2** (SP number, seismic file number, time, ...)
and the SP numbering system; h. streamer attitude: number/type/layback/interval of bearing
and depth sensors, magnetic declination, calibration; i. units of every quantity (exact
definition of feet).

### 4.2 Data record group [p.10-12]
One sample (shot or time) = **5 consecutive 80-byte records = 400 bytes**. A block holds 4 groups (20
records). Col 1 of **record 1** is blank (the data identifier). Cols 1 of records 2-5 hold data.
Records 1-3 are standard. Records 4-5 are "flexible" and must be described in the header; the
spec's layouts for them are only an example [p.12].

## 5. P3: land survey field data, SEG P3 (1983)

### 5.1 Header (mandatory free-text topics) [p.14-15]
a. area (country, state/province, county, region); b. client (operator, geophysical and survey
contractors, dates; optionally the surveyor's name and licence); c. surveying (method,
instruments, distance type: chain/stadia/EDM, azimuth basis, magnetic declination);
d. instrument calibration (serial numbers, dates); e. geodetic (as P1); f. projection (as P1,
plus the US State Plane zone name); g. units (distance units such as metres or US survey feet;
grid units; angle units: DMS, grads, quadrant); h. measurement data types (horizontal/vertical
angle origin and direction; slope vs horizontal distance); i. **detailed field formats and
data codes**: the formats of cols 37-80 and the meaning of the codes in cols 34-35.

### 5.2 Data record (one observation) [p.15-16]
| Cols | Len | Fmt | Field | Meaning |
|---|---|---|---|---|
| 1 | 1 | blank | `recordId` | blank |
| 2-17 | 16 | A16 | `lineName` | line name, left-justified |
| 18-33 | 16 | A16 | `pointId` | point identification number, **right-justified**, alphanumeric |
| 34-35 | 2 | A2 | `measurementType` | point/measurement type code, defined in the header (any alphanumerics) |
| 36 | 1 | I1 | `instrumentFace` | `1` = face I (direct), `2` = face II (telescope plunged 180°) |
| 37-44 | 8 | header | `horizontalAngle` | format in header |
| 45-51 | 7 | header | `verticalAngle` | vertical angle or differential height; format in header |
| 52-59 | 8 | header | `distance` | slope or horizontal distance, or stadia readings; format in header |
| 60-64 | 5 | header | `rodReading` | rod reading or EDM target height; format in header |
| 65-80 | 16 | header | `auxiliary` | auxiliary measurements / descriptors per header |

Rules [p.15-16]: each record is one observation of an instrument station, shotpoint, geophone
group, monument, control point or cultural feature. Repeated observations of the same object
go in separate, sequential records. The record order *is* the traverse order, so a writer must
preserve it.

## 6. Detection and file-level rules (all formats)

### 6.1 Distinguishing P1/P2/P3/P4 (1983)
There are no format codes. Use structure, then header text.

| Test (first data record after the header block) | Format |
|---|---|
| col 1 blank, col 35 ∈ {N,S}, col 45 ∈ {E,W}, cols 27-34 digits | **P1** |
| record *r* col 1 blank, record *r+1* col 9 ∈ {N,S} and col 19 ∈ {E,W}, record *r+1* col 1 digit; repeats every 5 records | **P2** |
| col 1 blank, col 36 ∈ {1,2}, cols 34-35 alphanumeric/blank, numeric text in 37-64 | **P3** |
| col 1 = `S`, cols 8-10 = `001` (or `  1`), next records numbered 2,3,4,5 in cols 8-10 | **P4** |
| tie-breaker: header text mentions "SEG P1/P2/P3/P4", "POSTPLOT", "SATELLITE", "THEODOLITE", ... | |

### 6.2 Header vs data on disk
The spec rule is that `H` in col 1 starts a 20-record header block, and the following 19
records are header *whatever their col 1*. Proposed reader modes: **strict** (count 20-record
blocks: a logical file's header = every block whose first record has `H`) and **lenient**
(default: after an `H` record, every record is header until the first record that validates as
a data record of the detected format; another `H` after data = new logical file). Writer: always
emit full 20-record header blocks (pad with blank records), with `H` in col 1 of each block's
first record and a blank col 1 elsewhere.

### 6.3 Other formats in the same files (not in this source)
SPS uses `H` + a 2-digit code and `S`/`R`/`X` records. UKOOA P1/90 and IOGP P1/11 use coded header
records (`H` followed by a numeric code, e.g. `H0100`) and type letters in col 1 of data
records. A P1/83 *data* record always has a blank col 1, and its header has no numeric codes.
These facts (from outside this source) are enough to reject non-1983 files. Do not parse those
formats with these layouts.

## 7. P4: Transit Doppler satellite field data, SEG P4 (1983)

### 7.1 Header topics [p.18-19]
a. area; b. client; c. antenna (type, model, serial, height of the electrical centre above the
monument or waterline, horizontal offset); d. receiver (type, model, serial, oscillator, nominal
frequency, Doppler count intervals); e. **Doppler record format description**; f.
information (refraction method, meteorological formats/units, status flags, antenna offset
units); g. geodetic (computed lat/long, datum, shifts).

### 7.2 Pass records [p.19-20]
Records are 80 columns. **`S` in col 1 marks the first line of every 20-line physical block**
(otherwise blank). Verified in Fig. D-1: `S` appears on the pass timing record and again on the
21st and 41st lines [p.21-22]. On disk, `S` therefore does **not** identify a record type: use
the record number in cols 8-10.

**Satellite pass timing record (record 001)** [p.19]
| Cols | Len | Field | Meaning |
|---|---|---|---|
| 1 | 1 | `formatDesignator` | `S` |
| 2-7 | 6 | `passId` | pass ID (sequential counter) |
| 8-10 | 3 | `recordNumber` | `001` |
| 11-20 | 10 | `date` | year, day number |
| 21-30 | 10 | `lockOnTime` | GMT hours, minutes at message sync of first lock-on |
| 31-40 | 10 | `estLatitude` | estimated latitude at lock-on |
| 41-50 | 10 | `estLongitude` | estimated longitude at lock-on |
| 51-60 | 10 | `estHeight` | estimated spheroidal height |
| 61-80 | 20 | `auxiliary` | optional temperature, pressure, auxiliary-system time |

> **AMBIGUITY:** [p.19, p.21] The sub-field layout inside cols 11-60 is unspecified. The
> example (blanks collapsed) reads `1979 187`, `2116`, `48 25`, `103 58`, `792.6`: deg/min with
> **no hemisphere or sign** (it is actually 103°58′ W). Keep these fields as text plus a
> best-effort parse.

**Satellite orbital data records 002-005 (optional 006-009)** [p.19-20]
| Cols | Len | Field | Meaning |
|---|---|---|---|
| 1 | 1 | `blockMark` | blank (`S` if first line of a block) |
| 2-7 | 6 | `passId` | as in record 001 |
| 8-10 | 3 | `recordNumber` | 002 / 003 = ephemeral words 1-7 / 8-14 (zero-fill if unused); 004 / 005 = Keplerian variables 1-7 / 8-14; 006-009 = the same, after an injection during the pass |
| 11, 21, ..., 71 | 1 each | `mv[1..7]` | majority-vote status char (coding in header) |
| 12-20, 22-30, ..., 72-80 | 9 each | `variable[1..7]` | majority-voted value |

**Satellite Doppler records (010 upward)** [p.20]: pass ID 2-7, record counter 8-10 (counting up
per Doppler interval). The rest of the layout is defined in header e. Fig. D-1 header: 400 MHz
count cols 13-20 ('.' at col 20), refraction cols 23-30 ('.' at col 26 per Fig. D-2), fractional
count cols 33-40 ('.' at col 36). Verified on the example: `560156.` ends at col 20, `-16.0364`
spans 23-30 with '.' at col 26, `-.6877` spans 35-40 with '.' at col 36.

> **AMBIGUITY:** [p.22] Fig. D-2 adds speed/heading or V-N/V-E at cols 37-42 and 41-46, which
> overlap each other and the fractional count (33-40). The example lines do not match any
> consistent column set. Treat Doppler records as header-defined: store the raw 80-column
> text, with an optional user-supplied column map.

P4 gives no seismic positions. Parse and round-trip only.

## 8. Implementation notes

### 8.1 Survey model and round-trip
- Keep every logical file as `{headerLines: seq[string] (80 col), records: seq[...]}`, and keep
  the raw 80-column text of every data record so that unknown/flexible fields round-trip.
- A writer re-emits fields from the parsed values *only* when they changed. Otherwise it writes
  the raw text (preserving implicit-decimal conventions, zero padding and OCR-odd content).
- Implicit decimals (`F8.X`, `F5.X`, P2 raw patterns) come from a per-logical-file setting:
  default 0, overridable by the user, never guessed from the header free text.
- Two-digit years: 1983-era data → 19YY. Proposal: a pivot (YY < 50 → 20YY), configurable.

### 8.2 Joining P1 to traces (`src/parseSEG/model/keys.nim`)
`GeometryTable` holds `sources`/`receivers: Table[StationKey, Coordinates]`, with
`StationKey(line, point: float64, index: int16)` (index 0 = matches any) and
`Coordinates(x, y, z)` (z may be NaN), filled by `addSource`/`addReceiver`.

| Format | Source positions | Receiver positions |
|---|---|---|
| **P1** | **yes**: every seismic-event data record is a source (shotpoint) position (the "point mapped" of header c, e.g. the airgun centre) | **none**: P1/83 has no receiver records |
| P2 | indirectly: vessel/system lat-long per shot (no grid, no offsets applied) | no |
| P3 | no coordinates (observations only); codes `S`/`G` are header-defined | no |
| P4 | no | no |

Proposed P1 → `addSource(line, point, index, x, y, z)` mapping:
| Key part | From | Rule |
|---|---|---|
| `line` | cols 2-17 (`lineName`, alphanumeric) | (1) trimmed name parses fully as a number → that number; (2) else look it up in a caller-supplied `Table[string, float64]` name→number map (CLI option / vendor map file); (3) opt-in heuristic: the trailing digit run (`CLT4960` → 4960), rejected if two distinct names map to the same number in one import; (4) else skip the record and report the line name once. Always keep `lineName` in the survey model. |
| `point` | cols 18-25 | `parseFloat(strip)`; skip non-seismic events (rule from the user, since there is no column for it) |
| `index` | col 26 reshoot | proposal: blank → 0 (wildcard), `A` → 2, `B` → 3, ... (the original shot is index 1 in SEG-D, so it falls back to the wildcard entry) |
| `x`, `y` | cols 46-53 / 54-61 | easting/northing with the per-file decimals. If blank, skip (no projection support); optionally use lon/lat degrees as x/y when the user asks |
| `z` | cols 62-66 | if the header/user says *elevation*: z = value. If *water depth*: z = NaN (TraceKeys z is elevation) and keep `waterDepth` in the survey model |

Refuse (or warn) when one import spans logical files with different projection header text.
TraceKeys from SEG-D 2.x carry `srcLine`/`srcPoint` as numbers, so the line mapping must match
how the acquisition system numbered the line.

## 9. Open questions
1. **Alphanumeric line names** vs the `float64` `StationKey.line`: use the numeric parse plus a
   name→number map (proposed above), or extend `StationKey` with a string line name (an API
   change). The owner must decide.
2. **Reshoot code → point index** mapping (blank→0, A→2, ...) is a proposal. SEG-D point index
   semantics differ by vendor.
3. **Implicit decimals** of F8.X/F5.X/raw patterns and DMS-vs-grads: default 0 / DMS with
   user override, or attempt header keyword parsing (`UNITS:`, `GRADS`)?
4. **Water depth vs elevation** in P1 cols 62-66: z = NaN, z = −depth, or z = value?
5. **Non-seismic event records** in P1: how does the user identify them (SP range, flag
   file, all included)?
6. **Header block handling on disk**: strict 20-record blocks vs lenient (proposed default).
7. **Two-digit year** pivot for writers of modern data.
8. **P2/P3/P4 depth**: full field parsing with round-trip (proposed), or opaque-text-only
   storage for P3/P4 and records 4-5 of P2?
9. P1/90 and P1/11 (the formats used by most modern survey files) are not covered. The
   owner should supply those specs if needed (PLAN task 10.1 notes this).
